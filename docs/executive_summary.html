Executive summary — how to submit, exactly

Binding spec: submission format · official rules (PDF) §3.2, §3.4 · upload budget: 3 submissions per week · one final submission per entity (§3.4).

2 · The “Predicted values must be in range [0, 1]” error — root cause and fix

Root cause (verified across sibling repos and consistent with the spec): the backend validator inspects the scored footprint pixels. If any pixel inside the footprint is NaN (or ±Inf, or <0, or >1), the form rejects the file with “Predicted values must be in range [0, 1]”. NaN outside the footprint is the official convention (“data outside the bounds is null or nan”) and is not the problem.

Permanent fix (build-time, not hope):

  1. Read the official sample submission as the template; derive the footprint mask = finite pixels of the template.
  2. Write predictions finite and clipped to [0, 1] on every footprint pixel (5,167,373 of them per sibling census — re-measure locally).
  3. Write NaN outside the footprint; set nodata=nan.
  4. Re-read the written file from disk with two independent range checks (whole-array nan-aware min/max and masked read) before offering it for upload. scripts/validate_submission.py does all of this.

Fallback only: if the form ever rejects a validator-passing NaN-outside file, mint a maximum-compatibility variant with 0.0 outside and no nodata tag. Under the published scorer the two are the same number (unscored pixels carry no weight), so this cannot change the score.

3 · Click-by-click upload

  1. Run python scripts/validate_submission.py candidate.tif --template sample_submission.tif. Proceed only on 13/13 PASS.
  2. Open the DrivenData submission page → “Make new submission”.
  3. File to submit: choose the validated .tif (or a .zip containing exactly one .tif).
  4. Note (optional): paste the unique note (§5). This is how the team tells submissions apart later.
  5. Submit. Record the returned public score next to the file's sha256 in Results the same day — never from memory later.
  6. Remember the budget: 3 submissions per week (rules §3.2, §3.4). A rejected-format upload still costs attention; a validated file never wastes a slot on format.

4 · Validate locally first (no upload needed)

python scripts/validate_submission.py candidate.tif --template sample_submission.tif
# 13 gates: band count, dtype, CRS, shape, transform, footprint finite,
# footprint range [0,1] (3 independent read paths), outside-NaN, nodata tag,
# profile-vs-template, sha256 + pixel census report.

The script prints the sha256, the finite/NaN census, and exactly which gate fails on which pixels. Gate list mirrors the sibling-validated 13-gate set so results are comparable.

5 · Unique-name + note convention (required)

Every candidate filename embeds hypothesis, date, and content id; every upload note pastes the same id:

file: gems18-<HYP>-<short-desc>-<YYYYMMDD>-<sha8>-nan.tif
note: 18GEMSDOE <HYP> | <short-desc> | id <sha8> | holdout <dense>/<sparse> vs best <..>

Example: gems18-E1-euler-depthgate-20261002-a1b2c3d4-nan.tif / 18GEMSDOE E1 | Euler depth-gated lineaments | id a1b2c3d4 | holdout 0.2xx/0.0xx vs best …. Never re-upload byte-identical files under new names — that is exactly how the group manufactured the phantom “0.1563 × N” record (see Results § duplicates). scripts/validate_submission.py prints the sha8 to paste.

6 · Slot discipline (binding)

  • No file is uploaded from this repo until its hypothesis beats the holdout best under the locked protocol — pre-registered direction, spatially blocked folds, locked final slice.
  • One hypothesis per slot; notes always carry the content id so ledger and board stay joinable.
  • Compliance: each human competes under one account / one team per the competition rules. The group's historical multi-account pattern is flagged for owner review (F08) — do not replicate it without written clearance.
