Why 0.1563 repeated

What we independently checked: the tracked submission TIFFs in public GEMSDOE and 5GEMSDOE are the exact same Git blob—Git SHA-1 812e61b74050d1350cc2bde1fab0c76ead32e0c4, 570,890 bytes. Their tracked sidecar submission_field.bin blobs also match, SHA-1 6a89b64e01a7c11b8235449c538390ac3435605d, 532,072 bytes. Byte-identical TIFFs necessarily contain the same prediction values.

What prior group records report: 16GEMSDOE’s public similarity registry associates the duplicate `GEMSDOE1`/`5GEMSDOE` artifact with a historical 0.1563 score and says `8GEMSDOE` differs only on pixels excluded under that project’s scored-pixel definition. We did not independently rerun that pixel-mask comparison or prove the exact upload-to-score mapping. In the current public GitHub account, `GEMSDOE1` is not a repository name; the registry uses it as a display label for `GEMSDOE`.

Why equal leaderboard rows are not evidence of equal files: the current snapshot separately lists SDCF9 and smashi34 at 0.1563. Equal rounded DTI scores do not show those accounts used the same raster. Nor do they resolve which historical file was uploaded under which account. The strongest explanation for the group’s duplicate 0.1563 record is repeated/near-identical predictions, but only the GEMSDOE/5GEMSDOE Git-blob identity is directly verified here.

Finding: duplicate artifact identity is proven for two public files; historical score attribution and all other 0.1563 rows remain unresolved. No claim is made that score equality proves file equality.
